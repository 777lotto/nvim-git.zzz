1. REQUIREMENTS                                           *git-panel-requirements*

Neovim 0.10 or newer and the Git executable on $PATH. Local Git views have no
Lua or Neovim plugin dependencies.

When installed, UX Chrome's optional ux_chrome.components API shares section
headers, file rows, and empty states. Foundation settings under
ux.chrome.components control padding, indentation, count spacing, and
truncation; ux.chrome.component.git.panel.navigation supplies overrides.
Presentation edits redraw cached data and preserve keyboard action targets.

GitHub repository views optionally use authenticated GitHub CLI (gh), or curl
with a token provider for private repositories. Curl can read public
repositories anonymously. GitHub CLI also enables GitHub repository creation
during a first push.

==============================================================================
2. INSTALLATION                                             *git-panel-installation*

With lazy.nvim: >lua

    {
      "777lotto/git-panel.nvim",
      cmd = { "GitPanel", "GitPanelSplit", "GitPanelConnection", "GitPanelDoctor" },
    }
<
The default bluff branch carries current development. Release tags provide
immutable tested versions.

Calling setup() is optional. See |git-panel-github| for configuration.

==============================================================================
3. COMMANDS                                                     *git-panel-commands*

:GitPanel             Open the dashboard in a tab page.
:GitPanelSplit        Open the dashboard as a left split.
:GitPanelConnection   Select a configured GitHub connection profile. An
                      optional profile name skips the first picker.
:GitPanelDoctor       Diagnose repository discovery and API reachability
                      without displaying credential values.

4. VIEWS AND KEYS                                                   *git-panel-keys*

The view bar contains:

1 Changes       Working-tree state, outgoing commits, branches, and worktrees.
2 History       Uncommitted files and recent commits.
3 Actions       Recent GitHub Actions workflow runs.
4 Issues        Open GitHub issues (pull requests are excluded).
5 Pull Requests Open GitHub pull requests.

The following mappings are local to the panel buffer:

<Tab>          Move to the next view.
<S-Tab>        Move to the previous view.
1 .. 5         Jump directly to a numbered view.
<CR>           Act on a section, branch, worktree, file, commit, push, or
               GitHub item. GitHub items open a Markdown summary in Neovim.
<NL>/<kEnter>  The LF and keypad forms of Enter perform the same action.
za             Fold or unfold the current section.
s / u          Stage or unstage the current file.
S / U          Stage all or unstage all.
x              Discard the current file changes after confirmation.
o / t          Resolve a conflict by taking ours or theirs, then stage it.
> / A          Continue or abort an in-progress Git operation.
c / C          Commit staged changes or stage everything and commit.
a              Amend the last commit.
b / R / d      Create, rename, or delete a branch.
m              Merge the branch under the cursor into the current branch.
W              Create a worktree.
F / P / f      Pull with --ff-only, push/publish, or fetch and prune.
               With no remote, P can create a GitHub repo using gh or attach
               an existing remote URL as origin, then push with tracking.
gx             Open the selected GitHub item in the system browser.
go / gd        Check out or diff the selected pull request against its base.
gc             Comment on the selected pull request after confirmation.
gm             Merge the selected pull request with the configured backend
               after confirmation.
gC / gD        Select a configured GitHub connection / diagnose API access.
L              Toggle full-tab and left-split layouts.
r              Refresh local state and force a GitHub synchronization.
? / g?         Open the structured, highlighted, scrollable key guide.
q              Close the panel. In a detail or key-guide window, close it.

Conflict workflows show the rebase-specific meaning of ours/theirs in the
operation banner. Remote branch renames use leases and avoid overwriting an
unrelated ref.

LOCAL SNAPSHOT AND RESPONSIVE LAYOUT                  *git-panel-responsive*

Independent local Git reads run concurrently; opening or changing a view does
not wait on a serial command chain. A generation guard prevents an older
snapshot from replacing newer state.

The full-tab layout adds a context rail at 120 columns or wider. It begins with
the repository root, upstream/sync state, remotes, GitHub metadata, and object
counts. Moving the cursor previews file diffs, commit stats, branch tips,
worktree status, tags, stashes, pushes, and GitHub items. Narrower tab pages
collapse to one pane. :GitPanelSplit always remains a compact fixed-width
control surface.

5. GITHUB INTEGRATION                                         *git-panel-github*

Entering Actions, Issues, or Pull Requests never blocks the Neovim UI. Cached
data renders immediately; a background request begins when the cache is stale.
Actions and Issues stay read-only. Pull-request comments and merges are the
only writes and always require confirmation. The panel distinguishes loading,
empty, stale, authentication, permission, rate-limit, network, and transport
states.

GitPanel detects GitHub.com and *.ghe.com SSH/HTTPS remotes, preferring origin.
Set github.host to identify a custom GitHub Enterprise Server host, or set
github.repository to OWNER/REPO when remote discovery is unsuitable. For a
proxy that mounts repositories under a path prefix, see
|git-panel-github-proxy|.

Repository metadata is fetched with the other cached views. The tab bar shows
open issue and pull-request counts plus the latest workflow state; the context
rail shows visibility, default branch, and description. Vanity metrics are not
shown.

Default configuration: >lua

    require("git_panel").setup({
      help = {
        border = "rounded",
        max_width = 88,
      },
      github = {
        enabled = true,
        profile = nil,             -- initial named profile
        profiles = {},             -- named non-secret setting overrides
        transport = "auto",       -- "auto", "gh", or "curl"
        repository = nil,          -- "OWNER/REPO"
        host = nil,                -- custom GitHub host
        remote_path_prefix = nil,  -- proxy path segments before OWNER/REPO
        api_url = nil,             -- custom HTTPS REST base; auto selects curl
        allow_insecure_http = false, -- permit a plaintext http:// api_url
        api_version = "2026-03-10",
        refresh_interval = 60,     -- seconds
        per_page = 30,             -- 1..100
        timeout = 15000,           -- milliseconds
        token_provider = nil,
        merge_backend = "api",     -- "api" or "signed_git"
        gh_command = "gh",
        curl_command = "curl",
      },
    })
<
The auto transport tries gh first, then curl. An ordinary authenticated gh
session requires no token configuration. GH_TOKEN, GITHUB_TOKEN, GH_HOST, and
the corresponding Enterprise variables follow GitHub CLI's own behavior.

github.gh_command may name a compatible API-only wrapper. GitPanel invokes it
as COMMAND api ENDPOINT [flags] and sets GH_HOST for the detected repository;
the wrapper does not need to implement other gh command groups.

CONNECTION PROFILES                              *git-panel-github-profiles*

github.profiles groups discovery, transport, endpoint, and merge settings
under user-facing names. github.profile selects the initial profile. The base
github settings remain available as the reserved "default" choice. >lua

    require("git_panel").setup({
      github = {
        profile = "team-broker",
        profiles = {
          ["github-cli"] = {
            label = "GitHub CLI",
            transport = "gh",
            gh_command = "gh",
          },
          ["team-broker"] = {
            label = "Team GitHub broker",
            description = "Credential-free repository API proxy.",
            transport = "curl",
            remote_path_prefix = "github/git",
            api_url = "https://broker.example/github/api",
          },
        },
      },
    })
<
:GitPanelConnection or gC switches the active profile for the current Neovim
process and immediately resets remote caches. Keep the durable default in
setup(). :GitPanelDoctor or gD shows the active profile, repository discovery,
available transport executables, and the result of a live metadata request.
It reports only whether an external provider is configured; it never asks for,
renders, or persists a token. "default" cannot be used as a profile key.

PROXIED GITHUB ENDPOINTS                          *git-panel-github-proxy*

A broker or reverse proxy may hold the credential, mount repositories under a
fixed path prefix, and publish a GitHub-compatible REST API elsewhere. A remote
such as https://proxy.example/github/git/OWNER/REPO.git is not discoverable by
default, because everything after the host must be exactly OWNER/REPO.

github.remote_path_prefix accepts a string or a list of strings and names the
segments removed before OWNER/REPO is read. A prefix is stripped only when the
remote carries it, so GitHub.com and *.ghe.com remotes are unaffected by a
configured proxy. github.api_url points the curl transport at the proxy REST
base and also makes that URL's host discoverable, so github.host is needed only
when the Git and API hosts differ. >lua

    require("git_panel").setup({
      github = {
        host = "proxy.example",
        remote_path_prefix = "github/git",
        api_url = "https://proxy.example/github/api",
      },
    })
<
A custom github.api_url selects the curl transport, so a proxy that injects the
credential upstream needs no token_provider.

github.allow_insecure_http permits a plaintext http:// github.api_url, for a
proxy that terminates TLS upstream and exposes only a private-network endpoint.
It relaxes the URL scheme check alone: GitPanel still refuses to send a bearer
token over plaintext HTTP to a non-loopback host, so a configuration mistake
cannot expose a credential on the wire. Use an https github.api_url when the
endpoint itself requires a token.

PULL-REQUEST MERGING                              *git-panel-github-merge*

github.merge_backend controls only gm. Pull-request comments and all view data
continue to use github.transport with either backend.

"api" is the portable default. GitHub creates the merge commit through the
REST API only if the PR head still matches the SHA shown in GitPanel. After a
successful merge, GitPanel deletes the remote head branch only when it belongs
to the base repository.

"signed_git" is available to anyone with Git commit signing and remote push
authentication configured. GitPanel fetches the current base and the pull
request's exact advertised head SHA, then creates a --no-ff --gpg-sign merge
in a temporary worktree. It verifies that the resulting commit has a
cryptographic signature and two parents before pushing the base with a normal,
non-force Git push. Git uses the configured OpenPGP, SSH, or S/MIME signing
format.

A same-repository head branch is deleted through Git with an exact-SHA lease.
Fork branches are never deleted. A signing failure or changed PR head aborts
without pushing; there is no unsigned or API fallback. Branch protection,
rulesets, or a merge queue can reject a direct push, in which case use the API
backend. The signed backend preserves the repository's configured Git remote
and needs that remote to permit a base-branch push.

An API-only App wrapper and signed Git transport can be configured separately:
>lua

    require("git_panel").setup({
      github = {
        gh_command = vim.fn.expand("~/.local/bin/gh-app"),
        merge_backend = "signed_git",
      },
    })
<

TOKEN PROVIDERS                                      *git-panel-github-auth*

The curl transport requires a bearer token for private repositories. A provider
may synchronously return a GitHub App user token, installation token, fine-
grained personal access token, or another accepted bearer token: >lua

    require("git_panel").setup({
      github = {
        transport = "curl",
        token_provider = function(context)
          return vim.env.GITHUB_TOKEN
        end,
      },
    })
<
An asynchronous provider accepts (context, done), returns true, then calls
done(token, error). This supports helpers that mint an installation token when
the previous token has expired: >lua

    token_provider = function(context, done)
      vim.system({ "my-app-token-helper", context.repository },
        { text = true }, function(result)
          vim.schedule(function()
            if result.code == 0 then
              done(vim.trim(result.stdout))
            else
              done(nil, "GitHub App token helper failed")
            end
          end)
        end)
      return true
    end
<
The context contains host, owner, name, and repository. GitPanel invokes the
provider for every request batch and never persists or displays the result.
Provider tokens are not placed in process arguments: gh receives one through
its environment; curl receives the authorization header over standard input,
ignores user-level curl configuration, and does not follow redirects.

A raw GitHub App private key is deliberately unsupported. The private key signs
a JWT used to mint an installation access token and should remain in an external
helper or vault. Installation tokens expire after one hour.

For these read-only views a GitHub App needs repository Actions: read,
Issues: read, and Pull requests: read permissions. Public resources may be read
without a token, subject to GitHub's anonymous API limits. gc additionally
needs Issues: write or Pull requests: write permission. The API merge backend
needs Contents: write for merging and same-repository branch deletion. The
signed Git backend instead relies on the Git remote's push authentication.

==============================================================================
6. LUA API                                                           *git-panel-api*

The module is returned by: >lua

    local git_panel = require("git_panel")
    git_panel.setup({})      -- optional
    git_panel.open("tab")    -- or "split"
    git_panel.select_view(3) -- Actions
    git_panel.select_connection() -- choose a configured connection profile
    git_panel.connection_doctor() -- test repository discovery and API access
    git_panel.refresh()
    git_panel.close()
<
setup() validates transport, merge_backend, and numeric GitHub settings. Calling
it again resets remote caches and keeps an open panel synchronized with the new
configuration.

7. BRANCHES AND SUPPORT                                      *git-panel-development*

Linux is tested on Neovim 0.10, 0.11, and 0.12. macOS is smoke-tested on the
current stable Neovim. Platform behavior is not separated into OS branches or
GitHub Environments.

Development branches start from and merge into the default bluff branch.
Signed tags and GitHub Releases mark tested bluff commits.
